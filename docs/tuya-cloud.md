# Tuya Cloud: подключение и сценарии

Ветка: `feature/tuya-cloud-scenarios`. Основная ветка `main` не изменяется.

## Какой язык сценариев выбрать

| Вариант | Возможности | Выбор для этого ESP8266 |
| --- | --- | --- |
| Визуальный ЕСЛИ → ТО, хранение JSON | Пороги, И/ИЛИ, гистерезис, расписания, выдержки, задержки, паузы и повторение; строгая проверка до сохранения | Реализован: понятен в браузере, ограничен по памяти, не исполняет произвольный код |
| Собственный текстовый DSL | Например `IF pvPower >= 2000 FOR 180s THEN ... AFTER 30s`; удобен для длинных правил | Возможное расширение; нужен отдельный синтаксический анализатор и редактор ошибок |
| Lua | Функции, переменные, циклы и сложные алгоритмы | Дополнительный интерпретатор и контроль ресурсов; для этой прошивки с TLS не выбран |
| Cron | Периодические календарные запуски | Дополнение к условиям, а не замена И/ИЛИ, выдержек и гистерезиса |

JSON служит форматом хранения, а не программой для eval. Движок имеет фиксированные возможности: максимум четыре сценария и три числовых условия на сценарий. Вложенные логические группы, переменные, произвольные скрипты и цепочки действий в этой версии отсутствуют. Для включения и выключения создаются отдельные сценарии.

## Подготовка

1. Arduino IDE: ESP8266 core **3.1.2**, плата **LOLIN(WEMOS) D1 R2 & mini**, CPU **160 MHz**. Дополнительно установите **ArduinoJson 6.21.5**. Остальные библиотеки поставляются с ядром ESP8266.
2. Загрузите все файлы папки `ANENJI_Dataloger` из этой ветки, включая `tuya_cloud.h`, `tuya_rules.h`, `tuya_page.h`.
3. На Tuya Developer создайте проект Smart Home, выберите центр данных вашего аккаунта, привяжите Smart Life/Tuya Smart через QR-код. Разрешите необходимые облачные API и проверьте срок доступа и квоты.
4. В API Explorer проверьте, что ваше устройство поддерживает стандартные API отправки команды и чтения состояния. Узнайте Device ID, код команды и точный тип значения. Код `switch_1` — пример, а не универсальная команда.
5. В верхней части панели откройте **Tuya Cloud / Облако Tuya** (`/tuya`). Введите Client ID, Secret и регион. Сохраните в EEPROM. Пустое поле Secret при последующем сохранении оставляет предыдущий секрет.
6. Экспортируйте доверенный **корневой CA** цепочки выбранного HTTPS-сервера Tuya в PEM из хранилища сертификатов/браузера, где сертификат сайта успешно проверяется. Вставьте PEM на странице Tuya и сохраните. Не подменяйте проверку цепочки `setInsecure()`; этого режима в прошивке нет. Максимум PEM — 4096 байт. При смене CA сервера файл может потребовать обновления.
7. Нажмите «Проверить подключение». Это запрашивает новый access token; команды устройствам не отправляются. Проверка доступна и при выключенной автоматике. После запуска есть пауза 30 секунд; нужен синхронизированный NTP.
8. Создайте правила с правильными Device ID/кодами/значениями. Новые правила выключены. После проверки настроек включите нужные правила и глобальную автоматику.

## Хранение

- `SettingsRecord` остаётся прежнего размера **128 байт**. Учётные данные Tuya занимают **108 байт с адреса 128** в существующей области настроек 0–255. Размер и адреса 240 записей истории не изменяются: резерв остаётся до 20 часов.
- Client ID, Secret, регион и включение интеграции защищены отдельной CRC16. EEPROM здесь — эмуляция flash, а не шифрованное хранилище. Секрет и токен не включаются в ответы HTTP и журналы. В репозитории их нет.
- Правила: `/TUYA.JSON` на SD; CA: `/TUYA.CA`. Сохранение использует временный файл и резервную копию. При загрузке правил есть восстановление из `/TUYA.JSON.BAK`.
- Сценарии, CA и учётные данные сохраняются без перезагрузки. Таймеры и состояние выполнения — только в RAM; при загрузке/изменении правил и подключении они стартуют заново. Команды должны задавать **идемпотентное значение**, например `true`/`false`, а не переключать toggle.
- Без SD работа Tuya приостанавливается. История инвертора продолжает использовать прежний резерв EEPROM. Если правила уже загружены, они остаются в RAM при кратковременном извлечении карты; на другую карту переносите JSON и CA вручную.

## Условия и время

Доступны: PV/нагрузка/сеть в Вт; заряд батареи в %; напряжения батареи, сети, PV и нагрузки; мощности заряда и разряда батареи. Мощность сети берётся из существующего положительного канала: экспорт в сеть не рассчитывается как отдельный избыток.

- Операторы: `>=`, `<=`, `>`, `<`. Условия объединяются одним **И** или **ИЛИ**.
- Гистерезис применяется к каждому условию. Пример: `PV >= 2000`, гистерезис 200 — активируется от 2000, остаётся активным до падения ниже 1800.
- Дни недели и окно времени используют выбранный в настройках часовой пояс. Начало равно концу — весь день. Окно `22:00–06:00` пересекает полночь; отметка дня относится к дню начала окна. Конец окна не включается.
- Нет числовых условий — сценарий по расписанию. Свежие данные инвертора всё равно обязательны.
- **Выдержка** требует, чтобы совокупное условие было непрерывно истинным. **Задержка действия** начинается после выдержки и также отменяется при нарушении условия, выходе из окна, потере Wi-Fi или устаревании данных.
- По умолчанию действие выполняется один раз за непрерывную активацию. Чтобы повторять при истинном условии, задайте период повтора >=60 секунд. 0 — без повтора.
- Минимальная пауза >=60 секунд учитывает подтверждённые действия всех правил с теми же Device ID и кодом команды. Она действует и между противоположными действиями включения и выключения.
- Приоритет — порядок сверху вниз: первое активное подходящее правило занимает свой Device ID/код. Нижние конфликтующие правила приостанавливаются. Проверять порядок особенно важно для защитного выключения: размещайте его выше включения.
- Таймеры и периоды ограничены семью сутками; сумма выдержки и задержки тоже <=7 суток. Используется монотонный millis с корректной обработкой переполнения. Это не точное выполнение по часам реального времени: команды могут задерживаться из-за опроса Modbus, TLS, сети и облака.

## Примеры правил

Все значения ниже — примеры, их нужно подобрать для своей батареи и нагрузки.

| Приоритет | ЕСЛИ | Выдержка / задержка | ТО |
| --- | --- | --- | --- |
| 1 | Батарея <=75%, гистерезис 3 | 30 с / 0 с | Реле `false` |
| 2 | Мощность сети >=500 Вт, гистерезис 100 | 60 с / 0 с | То же реле `false` |
| 3 | PV >=2000 Вт, гистерезис 200 **И** батарея >=95%, гистерезис 3; окно 10:00–17:00 | 180 с / 30 с | То же реле `true` |
| 4 | PV <=800 Вт, гистерезис 100 | 120 с / 0 с | То же реле `false` |

Снижение PV с 2000 до 1500 само по себе не выключит уже включённое реле: для выключения нужен отдельный сценарий. Конец окна тоже отменяет ожидающее действие, но **не создаёт обратную команду**; если требуется обязательное выключение вечером, выделите отдельное расписание для `false` вместо одного из четырёх правил.

## Сеть и подтверждение

- Подпись: SHA256 тела и HMAC-SHA256 с Client Secret, Client ID, timestamp, access token и канонической строкой метода/пути. HTTPS проверяет имя сервера, сертификаты и время.
- Токен хранится только в RAM. При истечении запрашивается новый. Между облачными обменами минимум 15 секунд; используются только запросы при необходимости и ручная проверка.
- POST: `/v1.0/iot-03/devices/{device_id}/commands`. Затем GET: `/v1.0/iot-03/devices/{device_id}/status`. Вариант API `/v2.0/cloud/thing/...` в этой версии не реализован.
- Успешный POST означает принятие команды. Выполнение отмечается только после совпадения запрошенного значения с состоянием, возвращённым облаком. Это последнее известное облаку состояние, а не независимое физическое измерение.
- После трёх неудачных попыток отправки/получения токена либо трёх неподтверждённых проверок правило приостанавливается до нарушения условия или повторного сохранения правил/параметров подключения/CA. Это предотвращает бесконечную отправку. Изменение параметров также начинает таймеры заново.
- Данные считаются свежими до трёх интервалов опроса, но не менее 30 и не более 300 секунд. При устаревании новые действия блокируются; автоматической обратной команды нет.
- На ESP8266 TLS синхронный: возможны паузы опроса и веб-ответов на время HTTPS. Ограничены тайм-ауты чтения/соединения; жёсткую верхнюю границу длительности DNS/TLS по ним обещать нельзя.
- Перед HTTPS проверяются свободная heap и размер свободного блока. При недостатке RAM действие откладывается/переходит в ограниченные попытки, без отключения проверки TLS. Отправка суточных samples переработана на блоки по 12 записей, чтобы освободить около 7,7 КБ статической RAM.
- Страница управления использует существующий локальный HTTP-сервер без отдельного пароля: открывайте её только в доверенной LAN и не пробрасывайте наружу. POST API требует `application/json`, CORS не разрешён. Это не заменяет аутентификацию пользователей локальной сети.

## Проверка

Полная сборка: ESP8266 core 3.1.2, Wemos D1 mini, CPU 160 MHz, ArduinoJson 6.21.5. Дополнительно пройдены тесты правил, UI EN/RU, записи EEPROM/CRC, валидации и сохранения JSON, совместимости языкового переключателя и X-масштабирования.

```sh
# Из корня репозитория; исполняемые файлы — временные.
g++ -std=c++11 -Wall -Wextra -pedantic tests/tuya_rules_test.cpp -o /tmp/tuya_rules_test
/tmp/tuya_rules_test
cd tests
npm install
npm test
```

На реальном ESP8266 и с аккаунтом/устройством Tuya новая интеграция пока не испытана. Первая проверка должна быть с выключенными сценариями и ручным тестом авторизации, затем с одной подходящей управляемой нагрузкой. Никаких реальных команд во время разработки не отправлялось.
