# Tuya Cloud: подключение и сценарии

Ветка: `feature/tuya-cloud-scenarios`. Основная ветка `main` не изменяется.

## Какой язык сценариев выбрать

| Вариант | Возможности | Выбор для этого ESP8266 |
| --- | --- | --- |
| Редактор выражений с кнопками, хранение JSON | Переменные, AND/OR/XOR/NOT, скобки, сравнения, гистерезис и отдельные таймеры | Реализован: ограниченный интерпретатор, без eval и произвольного кода |
| Полный текстовый DSL | Условия, действия и время в одном документе | Сейчас условие и SET уже текстовые; расписание и таймеры оставлены отдельными полями |
| Lua | Функции, переменные, циклы и сложные алгоритмы | Дополнительный интерпретатор и контроль ресурсов; для этой прошивки с TLS не выбран |
| Cron | Периодические календарные запуски | Дополнение к условиям, а не замена И/ИЛИ, выдержек и гистерезиса |

JSON служит форматом хранения, а не программой для eval. Доступны четыре сценария с ограниченным текстовым интерпретатором условий и одним действием SET. Для включения и выключения создаются отдельные сценарии. Старые файлы с плоскими условиями читаются; редактор преобразует их в выражения при сохранении. Файлы версии 2 не следует переносить в старую версию прошивки.

## Конструктор выражений

В каждом сценарии два редактора:

**ЕСЛИ**

```text
pvPower >= 2000 HYST 200 AND
NOT (batteryPercent < 95 OR gridPower > 100)
```

**ТО**

```text
SET("device_id", "switch_1", true)
```

Под полем условия — кнопки переменных, сравнений, AND, OR, XOR, NOT, скобок и HYST. Под полем действия — SET, аргументы, логические значения и разделители. Кнопка вставляет текст в позицию курсора или заменяет выделение. Проверка синтаксиса идёт при вводе; позиция ошибки показывается рядом с условием. Сервер повторно проверяет выражение и действие перед записью.

- Приоритет: сравнения → NOT → AND → XOR → OR. Используйте скобки для явных групп. `XOR` истинен, когда истинно ровно одно из двух выражений; цепочка XOR вычисляет нечётность числа истинных операндов.
- Имена переменных чувствительны к регистру; операторы AND/OR/XOR/NOT/HYST пишутся прописными буквами. `true` и `false` — строчными.
- Сравнения: `>=`, `<=`, `>`, `<`, `==`, `!=`. Числа допускают знак, десятичную точку и экспоненту. Неявного преобразования чисел в логические значения нет: пишите `pvPower > 0`, а не `pvPower`.
- Можно сравнивать переменные друг с другом, например `pvPower > loadPower`. Арифметика, функции, строки в условиях, присваивания и циклы отсутствуют.
- Кроме измерений доступны `hour` (0–23), `minute` (0–59), `minuteOfDay` (0–1439), `weekday` (Пн=1…Вс=7). Часовой пояс — из настроек устройства.
- Необязательный суффикс `HYST 200` задаёт гистерезис конкретного сравнения. Для `==`/`!=` гистерезис должен быть нулевым. Состояния сравнения отслеживаются независимо, в том числе внутри NOT и вложенных групп.
- Ограничения условия: 192 ASCII-символа, 96 токенов, 12 сравнений и 8 уровней вложенности/NOT. Интерпретатор условий не использует heap.
- Действие: только `SET("Device ID", "код", значение)`. Значение — JSON boolean, конечное число или строка в кавычках, максимум 66 байт в JSON-представлении. Device ID — до 64 ASCII-символов, код — до 40; разрешены буквы, цифры, `_` и `-`. Максимум действия — 256 символов. Никаких вызовов произвольных функций или цепочек команд.
- Выдержка, задержка, расписание, приоритет, минимальная пауза и период повтора остаются отдельными полями. Они применяются к результату всего условия.

## Подготовка

1. Arduino IDE: ESP8266 core **3.1.2**, плата **LOLIN(WEMOS) D1 R2 & mini**, CPU **160 MHz**. Дополнительно установите **ArduinoJson 6.21.5**. Остальные библиотеки поставляются с ядром ESP8266.
2. Загрузите все файлы папки `ANENJI_Dataloger` из этой ветки, включая `tuya_cloud.h`, `tuya_rules.h`, `tuya_expression.h`, `tuya_devices.h`, `tuya_page.h`.
3. На Tuya Developer создайте проект Smart Home, выберите центр данных вашего аккаунта, привяжите Smart Life/Tuya Smart через QR-код. Разрешите необходимые облачные API и проверьте срок доступа и квоты.
4. В API Explorer проверьте, что ваше устройство поддерживает стандартные API отправки команды и чтения состояния. Узнайте Device ID, код команды и точный тип значения. Код `switch_1` — пример, а не универсальная команда.
5. В верхней части панели откройте **Tuya Cloud / Облако Tuya** (`/tuya`). Введите Client ID, Secret и регион. Сохраните в EEPROM. Пустое поле Secret при последующем сохранении оставляет предыдущий секрет.
6. Экспортируйте доверенный **корневой CA** цепочки выбранного HTTPS-сервера Tuya в PEM из хранилища сертификатов/браузера, где сертификат сайта успешно проверяется. Вставьте PEM на странице Tuya и сохраните. Не подменяйте проверку цепочки `setInsecure()`; этого режима в прошивке нет. Максимум PEM — 4096 байт. При смене CA сервера файл может потребовать обновления.
7. Нажмите «Проверить подключение». Это запрашивает новый access token; команды устройствам не отправляются. Проверка доступна и при выключенной автоматике. После запуска есть пауза 30 секунд; нужен синхронизированный NTP.
8. Создайте правила с правильными Device ID/кодами/значениями. Новые правила выключены. После проверки настроек включите нужные правила и глобальную автоматику.

## Список устройств из облака

На странице Tuya есть раздел **«Устройства Tuya»**:

1. Скопируйте **UID привязанного аккаунта** из Tuya Developer → проект → Devices → Link App Account. UID аккаунта и Client ID проекта — разные значения. При создании облачного проекта должна быть выполнена привязка нужного аккаунта Smart Life / Tuya Smart.
2. Введите UID и нажмите **«Обновить устройства»**. Используются сохранённые Client ID, Secret, регион и CA. Запрос списка доступен и при выключенной автоматике; он не отправляет команд устройствам.
3. Первые три устройства появятся с именами, Device ID, категориями и статусами связи. **«Следующие 3 устройства»** загружает следующую страницу и добавляет её к показанному в браузере списку. Повторное обновление начинает список с первой страницы.
4. В редакторе действия выберите устройство и нажмите **«Подставить устройство в SET»**. У корректного действия меняется только первый аргумент: код команды и значение сохраняются. Если действие ещё не дописано, Device ID вставляется строкой в позицию курсора.

Выберите устройство в редакторе действия и нажмите «Загрузить функции». Через GET `/v1.2/iot-03/devices/{device_id}/specification` загружается полный стандартный набор доступных команд (`functions`, без read-only `status`). Затем выберите команду и значение, нажмите «Вставить SET». Boolean, Enum, Integer и String проверяются по типу и ограничениям; Integer вводится в сырых единицах Tuya с учётом показанного scale. Json/Raw/Bitmap требуют отдельной поддержки и автоматически не вставляются. Загрузка не отправляет команд устройству. Последняя спецификация сохраняется на SD в `/TUYA.FUN`, с привязкой к UID, устройству, Client ID и региону. Ответ ограничен 24 КБ и 4 КБ памяти JSON; при превышении запрос завершается ошибкой, список не обрезается. Требуется разрешение API спецификации устройства в проекте Tuya.

Реализация:

- `GET /v1.2/iot-03/devices` с `source_type=tuyaUser`, `source_id=UID`, `page_size=3` и `last_row_key`. Параметры сортируются и URL-кодируются до вычисления подписи.
- Облачный запрос выполняется через существующую очередь цикла, а веб-запрос сразу получает номер задания. Токен получается отдельным шагом. Между облачными обменами сохраняется пауза 15 секунд; подтверждение уже отправленной команды и готовые действия сценариев имеют приоритет перед каталогом. Максимальное время ожидания задания — 120 секунд. Ручная загрузка обслуживается также во время ожидания входящего TCP-соединения инвертора, без выполнения сценариев в этом ожидании.
- Ответ читается потоково с JSON-фильтром: сохраняются только `id`, `name`, `category`, `online` и метаданные пагинации. Local Key, IP, координаты и прочие поля не передаются в UI, не сохраняются на SD и не выводятся в журнал. Размер входного ответа ограничен 24 КБ, JSON-пул страницы — 1536 байт. Слишком большой/некорректный ответ возвращает ошибку вместо роста памяти.
- UID записывается на SD в `/TUYA.ACC`; последняя успешная страница — в `/TUYA.DEV`. EEPROM и его формат не меняются. Кэш привязан к UID, Client ID и региону; продолжение страницы от другого аккаунта или старого курсора отклоняется.
- На ESP8266 не накапливается весь каталог: текущая страница содержит до трёх устройств. Просмотренные страницы объединяет браузер. После перезапуска браузера восстанавливается только последняя сохранённая страница, помеченная **«из кэша»**, а не весь просмотренный список. Статусы связи в кэше могут быть устаревшими; нажмите «Обновить устройства» для свежего списка.
- При смене UID список и варианты выбора очищаются; при смене Client ID/региона старый кэш не используется. Привязка аккаунта и разрешения проекта определяют, какие устройства доступны. При ошибке облака старая успешная страница не затирается.

Локальный API: `POST /api/tuya/devices` принимает `{ "uid": "...", "cursor": "" }` и возвращает `202` с `jobId`. `GET /api/tuya/devices` возвращает состояние задания, ошибку, сохранённый UID и последнюю страницу текущего аккаунта. Второй одновременный запрос получает `409`. CORS не включён; POST требует JSON.

## Хранение

- `SettingsRecord` остаётся прежнего размера **128 байт**. Учётные данные Tuya занимают **108 байт с адреса 128** в существующей области настроек 0–255. Размер и адреса 240 записей истории не изменяются: резерв остаётся до 20 часов.
- Client ID, Secret, регион и включение интеграции защищены отдельной CRC16. EEPROM здесь — эмуляция flash, а не шифрованное хранилище. Секрет и токен не включаются в ответы HTTP и журналы. В репозитории их нет.
- Правила: `/TUYA.JSON` на SD; CA: `/TUYA.CA`; UID аккаунта: `/TUYA.ACC`; последняя страница списка устройств: `/TUYA.DEV`. Сохранение использует временный файл и резервную копию. При загрузке правил есть восстановление из `/TUYA.JSON.BAK`.
- Сценарии, CA и учётные данные сохраняются без перезагрузки. Таймеры и состояние выполнения — только в RAM; при загрузке/изменении правил и подключении они стартуют заново. Команды должны задавать **идемпотентное значение**, например `true`/`false`, а не переключать toggle.
- Без SD работа Tuya приостанавливается. История инвертора продолжает использовать прежний резерв EEPROM. Если правила уже загружены, они остаются в RAM при кратковременном извлечении карты; на другую карту переносите JSON и CA вручную.

## Условия и время

Доступны: PV/нагрузка/сеть в Вт; заряд батареи в %; напряжения батареи, сети, PV и нагрузки; мощности заряда и разряда батареи. Мощность сети берётся из существующего положительного канала: экспорт в сеть не рассчитывается как отдельный избыток.

- Составные условия поддерживают AND, OR, XOR, NOT, скобки и все шесть сравнений. Подробности синтаксиса — выше.
- Гистерезис применяется к каждому условию. Пример: `PV >= 2000`, гистерезис 200 — активируется от 2000, остаётся активным до падения ниже 1800.
- Дни недели и окно времени используют выбранный в настройках часовой пояс. Начало равно концу — весь день. Окно `22:00–06:00` пересекает полночь; отметка дня относится к дню начала окна. Конец окна не включается.
- Условие `true` — сценарий только по расписанию. Свежие данные инвертора всё равно обязательны.
- **Выдержка** требует, чтобы совокупное условие было непрерывно истинным. **Задержка действия** начинается после выдержки и также отменяется при нарушении условия, выходе из окна, потере Wi-Fi или устаревании данных.
- По умолчанию действие выполняется один раз за непрерывную активацию. Чтобы повторять при истинном условии, задайте период повтора >=60 секунд. 0 — без повтора.
- Минимальная пауза >=60 секунд учитывает подтверждённые действия всех правил с теми же Device ID и кодом команды. Она действует и между противоположными действиями включения и выключения.
- Приоритет — порядок сверху вниз: первое активное подходящее правило занимает свой Device ID/код. Нижние конфликтующие правила приостанавливаются. Проверять порядок особенно важно для защитного выключения: размещайте его выше включения.
- Таймеры и периоды ограничены семью сутками; сумма выдержки и задержки тоже <=7 суток. Используется монотонный millis с корректной обработкой переполнения. Это не точное выполнение по часам реального времени: команды могут задерживаться из-за опроса Modbus, TLS, сети и облака.

## Примеры правил

Все значения ниже — примеры, их нужно подобрать для своей батареи и нагрузки.

| Приоритет | ЕСЛИ | Выдержка / задержка | ТО |
| --- | --- | --- | --- |
| 1 | Батарея <=75%, гистерезис 3 | 30 с / 0 с | Реле `false` |
| 2 | Мощность сети >=500 Вт, гистерезис 100 | 60 с / 0 с | То же реле `false` |
| 3 | PV >=2000 Вт, гистерезис 200 **И** батарея >=95%, гистерезис 3; окно 10:00–17:00 | 180 с / 30 с | То же реле `true` |
| 4 | PV <=800 Вт, гистерезис 100 | 120 с / 0 с | То же реле `false` |

Снижение PV с 2000 до 1500 само по себе не выключит уже включённое реле: для выключения нужен отдельный сценарий. Конец окна тоже отменяет ожидающее действие, но **не создаёт обратную команду**; если требуется обязательное выключение вечером, выделите отдельное расписание для `false` вместо одного из четырёх правил.

## Сеть и подтверждение

- Подпись: SHA256 тела и HMAC-SHA256 с Client Secret, Client ID, timestamp, access token и канонической строкой метода/пути. HTTPS проверяет имя сервера, сертификаты и время.
- Токен хранится только в RAM. При истечении запрашивается новый. Между облачными обменами минимум 15 секунд; используются только запросы при необходимости и ручная проверка.
- POST: `/v1.0/iot-03/devices/{device_id}/commands`. Затем GET: `/v1.0/iot-03/devices/{device_id}/status`. Вариант API `/v2.0/cloud/thing/...` в этой версии не реализован.
- Успешный POST означает принятие команды. Выполнение отмечается только после совпадения запрошенного значения с состоянием, возвращённым облаком. Это последнее известное облаку состояние, а не независимое физическое измерение.
- После трёх неудачных попыток отправки/получения токена либо трёх неподтверждённых проверок правило приостанавливается до нарушения условия или повторного сохранения правил/параметров подключения/CA. Это предотвращает бесконечную отправку. Изменение параметров также начинает таймеры заново.
- Данные считаются свежими до трёх интервалов опроса, но не менее 30 и не более 300 секунд. При устаревании новые действия блокируются; автоматической обратной команды нет.
- На ESP8266 TLS синхронный: возможны паузы опроса и веб-ответов на время HTTPS. Ограничены тайм-ауты чтения/соединения; жёсткую верхнюю границу длительности DNS/TLS по ним обещать нельзя.
- Перед HTTPS проверяются свободная heap и размер свободного блока. При недостатке RAM действие откладывается/переходит в ограниченные попытки, без отключения проверки TLS. Отправка суточных samples переработана на блоки по 12 записей, чтобы освободить около 7,7 КБ статической RAM.
- Страница управления использует существующий локальный HTTP-сервер без отдельного пароля: открывайте её только в доверенной LAN и не пробрасывайте наружу. POST API требует `application/json`, CORS не разрешён. Это не заменяет аутентификацию пользователей локальной сети.

## Проверка

Полная сборка: ESP8266 core 3.1.2, Wemos D1 mini, CPU 160 MHz, ArduinoJson 6.21.5. Дополнительно пройдены тесты правил, UI EN/RU, записи EEPROM/CRC, валидации и сохранения JSON, совместимости языкового переключателя и X-масштабирования.

```sh
# Из корня репозитория; исполняемые файлы — временные.
g++ -std=c++11 -Wall -Wextra -pedantic tests/tuya_rules_test.cpp -o /tmp/tuya_rules_test
/tmp/tuya_rules_test
g++ -std=c++11 -Wall -Wextra -pedantic tests/tuya_expression_test.cpp -o /tmp/tuya_expression_test
/tmp/tuya_expression_test
cd tests
npm install
npm test
```

На реальном ESP8266 и с аккаунтом/устройством Tuya новая интеграция пока не испытана. Первая проверка должна быть с выключенными сценариями и ручным тестом авторизации, затем с одной подходящей управляемой нагрузкой. Никаких реальных команд во время разработки не отправлялось.

### Память TLS и диагностика

Суточный буфер истории выделяется только во время чтения графиков и освобождается после ответа: около 4,9 КБ RAM доступны остальной прошивке. Память JSON-ответа облака выделяется после TLS-рукопожатия. Перед подключением проверяется наличие и корректность `/TUYA.CA`; отсутствие сертификата теперь сообщает `ca_required`, а не маскируется проверкой RAM.

Для выбранного сервера раз в час проверяется поддержка TLS MFLN 1024. Только при положительном ответе используется RX-буфер 1024 байта, иначе остаётся полный 16384 байта. Проверка цепочки, имени сервера и срока действия сертификата сохраняется. Статус показывает свободную RAM, максимальный непрерывный блок, показатели перед TLS, размер RX-буфера и числовой код ошибки BearSSL. Значения текущей RAM снимаются до выделения JSON документа статуса. Без подходящего CA подключение не выполняется. Проверки памяти остаются: 29 КБ / блок 18 КБ для полного буфера, 15 КБ / блок 7 КБ для подтверждённого MFLN; это предварительная оценка, фактические ошибки выделения также обрабатываются.

Дополнительный тест времени жизни буфера истории: `python3 tests/sample_cache_test.py` (нужен g++).
